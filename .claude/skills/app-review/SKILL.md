# mementolane-app レビュー

`$ARGUMENTS` で指定された対象（省略時は現在の差分）をレビューし、**コードレビュー**と**パフォーマンスレビュー**の結果を 1 つのレポートに統合して出力する。

## 前提: レビュー対象外

以下は指摘しない（どちらのレビューでも除外する）。

- `src/components/ui/` 配下
  - shadcn CLI で生成したコンポーネントで、CLI 更新時に差分が出ないよう手を加えない方針のため。
  - `data-checked:` や `data-horizontal:` などのバリアントは `shadcn/tailwind.css` の `@custom-variant` で定義済みであり、記法ミスではない。
- `dist/`、`node_modules/`、`package-lock.json`、`src-tauri/Cargo.lock`、`src-tauri/gen/`、`src-tauri/icons/`

## 手順

### 1. 対象を確定する

- 引数に PR 番号・ブランチ・パスがあればそれを対象にする。なければ `main` との差分（未コミット分を含む）を対象にする。
- 対象の変更ファイル一覧を取得し、上記の対象外ファイルを除く。対象が空なら 🟢 で終了する。

### 2. パフォーマンスレビューをバックグラウンドで開始する

Agent ツール（`general-purpose`）で、下記「パフォーマンスレビューの観点」を渡してパフォーマンスレビューを依頼する。コードレビューと並行して進めるため、先に起動しておく。

エージェントへの依頼内容:

- 対象の差分と、その差分が呼び出す／呼び出される周辺コードを読むこと
- 実際にパフォーマンスへ影響する問題のみを挙げ、推測だけの指摘は含めないこと
- 各指摘について「ファイル:行」「問題の内容」「どのような状況で遅くなる／重くなるか」「改善案」「重大度（🔴🟡🔵）」を返すこと
- 上記の対象外ファイルは指摘しないこと

### 3. code-review スキルでコードレビューを実行する

Skill ツールで `code-review` を呼び出す。引数には手順 1 で確定した対象と、`$ARGUMENTS` で指定されたレベル（なければ省略）を渡す。

- code-review の結果はそのまま最終出力にせず、手順 4 で統合するための材料として扱う。
- code-review が `src/components/ui/` など対象外ファイルを指摘した場合は除外する。

### 4. 結果を統合して出力する

- 2 つのレビュー結果を突き合わせ、同じ箇所・同じ原因の指摘は 1 件にまとめる。
- 各指摘は該当コードを自分で確認し、誤検知は除外する。
- 各指摘に重大度を付ける（下記基準）。並び順は 🔴 → 🟡 → 🔵。
- 全体の判定は、指摘の中で最も高い重大度とする。指摘が 0 件なら 🟢（approved）。
- 下記「出力フォーマット」に従って日本語で出力する。

## 重大度の基準

| 記号 | 意味         | 目安                                                                                         |
| ---- | ------------ | -------------------------------------------------------------------------------------------- |
| 🔴   | 改善必須     | バグ・データ破損／消失・クラッシュ・セキュリティ問題・ユーザー操作で確実に体感できる性能劣化 |
| 🟡   | 改善推奨     | 特定条件で起きる不具合、データ量増加で顕在化する性能問題、保守性を大きく下げる実装           |
| 🔵   | 影響度が低い | 軽微な非効率、可読性・命名・重複などの改善                                                   |
| 🟢   | 問題なし     | 指摘 0 件（approved）                                                                        |

## パフォーマンスレビューの観点

このアプリは Tauri 2（Rust）+ React 19 + Vite + `@tauri-apps/plugin-sql`（SQLite）+ zod + react-hook-form で構成されている。以下を重点的に確認する。

### SQLite / リポジトリ層（`src/repositories/`, `src/lib/db.ts`, `src-tauri/src/lib.rs`）

- DB 呼び出しは 1 回ごとに Tauri IPC の往復が発生する。ループ内の `select` / `execute`（N+1）や、不要な事前・事後の再取得が増えていないか
- 一括処理が 1 件ずつの `execute` になっていないか（トランザクションや 1 クエリにまとめられないか）
- `WHERE` / `ORDER BY` で使う列（`completed`, `status`, `due_at` など）に対するインデックスの要否。マイグレーション追加時は既存バージョンを書き換えず新バージョンで追加しているか
- `SELECT *` や不要な列・行の取得、全件取得してからフロントでフィルタしていないか
- `getDb()` のシングルトンを経由せず `Database.load` を重複して呼んでいないか
- 大量行に対する zod の `safeParse` など、取得結果の検証コストが過大になっていないか

### React（`src/pages/`, `src/components/task/`）

- `useEffect` の依存配列の誤りによる再実行・無限ループ、アンマウント後の `setState`
- リスト全体を再レンダリングさせる状態設計（親の state 更新で全カードが再描画される等）。`useMemo` / `useCallback` / `memo` が必要な箇所と、逆に不要な過剰メモ化
- `key` に index を使っている、または不安定な `key` による再マウント
- レンダー中の重い計算・毎回の新規オブジェクト／配列生成が子の再レンダリングを誘発していないか
- 更新後に全件再取得していないか（楽観的更新や差分反映で済まないか）
- react-hook-form の `watch` の多用など、入力ごとのフォーム全体再レンダリング

### バンドル / 起動

- `lucide-react` などはアイコン単位の named import になっているか。重い依存の追加や、ページ単位で遅延読み込みすべきものがないか
- `vite.config.ts`・`tauri.conf.json`・`Cargo.toml` の `[profile.release]` の変更がサイズや起動時間を悪化させていないか

### Rust（`src-tauri/`）

- コマンドやセットアップ処理でメインスレッドをブロックする同期 I/O・重い処理
- 不要な `clone` や大きなデータのシリアライズ往復

## 出力フォーマット

最初に全体の判定（重大度とその判断理由を簡潔に）を書き、続けて指摘ごとの詳細を書く。

```
## レビュー結果

🔴 {○○のため改善が必要です}

### 1. {指摘の要約}
- 重大度: 🔴 改善必須
- 指摘箇所: `src/repositories/task-repository.ts:72`
- 改善案: {何が問題で、どう直すか。必要ならコード例}

### 2. {指摘の要約}
- 重大度: 🟡 改善推奨
- 指摘箇所: `src/pages/Index.tsx:18`
- 改善案: ...
```

- 全体判定の文言は重大度に合わせる。
  - 🔴: `🔴 {理由}のため改善が必要です`
  - 🟡: `🟡 {理由}のため改善を推奨します`
  - 🔵: `🔵 軽微な指摘のみです（{理由}）`
- 指摘箇所は `ファイル名:行数` 形式（範囲なら `ファイル名:開始行-終了行`）。複数箇所にまたがる場合は列挙する。
- 指摘ごとに、コードレビュー由来かパフォーマンスレビュー由来かは書かなくてよい。

指摘が 0 件の場合は以下のみを出力する。

```
## レビュー結果

🟢 approved
{確認した範囲と、問題がないと判断した理由を 1〜2 文で}
```
